① Node 超时的处理机制

▎ HSDF 框架里每个 Node 在 Graph 里声明时可以配置超时时间和降级策略。底层是 CompletableFuture + 自定义的 FutureUtils.getFuture(timeout)，超时后不抛异常，而是返回一个预定义的降级值。
▎
▎ 具体分两类处理：
▎
▎ 非核心 Node（如评论数、推荐语）：超时直接返回 null 或空集合，BFF 层做好 null 判断，前端该字段不展示即可，不影响主流程。
▎
▎ 核心 Node（如商品价格、下单跳链）：如果这个 Node 的结果是后续 Node 的强依赖，超时会触发整个依赖链的降级——上层 BFF 判断关键字段缺失后，可以走整体降级策略，比如返回缓存的上一次结果，或者返回一个兜底的静态页面，而不是直接返回空让前端白屏。
▎
▎ 我们遇到过一次下游商品服务超时抖动，由于商品 Node 是核心 Node，触发了整个 BFF 降级。当时的处理是：短时间走本地缓存兜底（TTL 5 分钟），同时告警通知下游团队。大约 10 分钟后下游恢复，缓存自动失效，链路恢复正常，用户感知到的只是推荐语消失了几分钟，主流程未受影响。

② 线上超时如何发现和定位

▎ 定位流程大致是这样的：

▎ 1. 告警触发 → 看 CAT 的接口成功率曲线，确认是偶发还是持续

知识补课

一、DAG 图是什么

DAG = Directed Acyclic Graph，有向无环图。

在 HSDF 框架里，你调用的每个下游服务是一个 Node，Node 之间的依赖关系构成一张图：

         ┌──── 商品Node ────┐
请求入口 ──┤                  ├──→ BFF聚合 ──→ 返回前端
         └──── 搜推Node ────┘
                ↑
           必须先跑完
              营销Node

Directed（有向）：A 依赖 B，所以 B 必须先执行完，A 才能开始。
Acyclic（无环）：不能 A 依赖 B，B 又依赖 A，否则死锁。
好处：没有依赖关系的 Node 可以并行执行，大幅降低总耗时。

面试里你可以这样说：

▎ "DAG 是有向无环图，HSDF 用它描述 Node 间的依赖关系，没有依赖的 Node 并行跑，有依赖的 Node 按顺序跑，这样编排的结果是总耗时等于最长串行链路的耗时，而不是所有 Node 的耗时之和。"

二、Caffeine + Redis 二级缓存一致性

为什么需要两级缓存？

┌──────┬─────────────────────┬───────────────────┐
│      │  Caffeine（本地）   │   Redis（远程）   │
├──────┼─────────────────────┼───────────────────┤
│ 速度 │ 纳秒级（内存直取）  │ 毫秒级（网络 IO） │
├──────┼─────────────────────┼───────────────────┤
│ 容量 │ 小（受 JVM 堆限制） │ 大                │
├──────┼─────────────────────┼───────────────────┤
│ 共享 │ ❌ 每台机器独立     │ ✅ 所有实例共享   │
└──────┴─────────────────────┴───────────────────┘

一致性问题在哪？

实例A的Caffeine: 场景X = [热点1, 热点2]   ← 过期时间还剩3分钟
Redis:           场景X = [热点1, 热点3]   ← 刚被运营更新
实例B的Caffeine: 场景X = [热点1, 热点3]   ← 刚从Redis同步

→ 同一时刻，实例A和实例B返回给用户的数据不一致。

三种解决方案：

方案1: TTL过期（最简单）
  → Caffeine设置短TTL（如30秒），过期后重新从Redis加载
  → 缺点：最多有30秒不一致窗口

方案2: 消息广播（强一致）
  → Redis数据更新时，发一条MQ消息给所有实例
  → 每个实例收到消息后主动删除本地Caffeine缓存
  → 下次请求时重新加载
  → 缺点：需要维护消息通道，复杂度高

方案3: 版本号比较
  → 每次从Caffeine取数据时，顺带检查Redis里的版本号
  → 版本不一致则主动失效本地缓存

门票场景化用哪种？ 你可以说：

▎ "我们用的是 TTL + 消息广播结合的方案。热点数据 Caffeine TTL 设 30 秒兜底，运营主动修改场景配置时发 MQ 通知各实例立即失效本地缓存，保证运营操作能在秒级生效。"

三、缓存倾斜 vs 热点 Key（你的描述基本对）

你说的「大量请求打到缓存A服务器」，这其实更准确的叫法是缓存热点（Hot Key）——某一个 Key 被大量读写，导致该 Key 所在的 Redis 分片压力过大。

缓存倾斜严格来说是数据分布不均，某个分片数据量远多于其他分片（存储倾斜），和热点稍有不同，但实际场景里经常混用，你的描述方向是对的。

热点 Key 的常见解法：

1. 本地缓存兜底（就是上面的 Caffeine）
   → 热点请求直接打本地，不走 Redis

2. Key 打散
   → 把一个热点 Key 复制成多个 Key（如 scene:123:0 ~ scene:123:9）
   → 读的时候随机选一个，写的时候更新所有
   → 适合读多写少的场景

3. 读写分离 + 扩容
   → Redis 集群扩从节点，让读流量分散到多个副本

① 索引设计 — 查询1有误，查询2正确但没说清理由

查询1：❌ 建两个独立索引是错的

WHERE user_id = 123 ORDER BY create_time DESC LIMIT 10

你说「建 user_id 和 create_time 两个索引」——MySQL 只会选一个用，另一个浪费。

正确答案是建联合索引 (user_id, create_time)：

B+ 树叶节点排列：
[user_id=100, time=1月] → [user_id=100, time=3月]
[user_id=123, time=2月] → [user_id=123, time=5月] ← 直接定位
[user_id=200, time=1月] → ...

MySQL 先用 user_id=123 定位到对应区间，
再在该区间内 create_time 已经有序，
ORDER BY 不需要 filesort，直接按顺序取 10 条。

查询2：✅ (status, create_time) 正确，但理由要说完整

▎ 为什么 status 在前？因为 status 是等值查询（=），create_time 是范围查询（BETWEEN）。B+ 树里，范围查询之后的列无法继续走索引，所以等值列必须放前面，让范围列用上索引。反过来建 (create_time, status) 的话，status 就用不上了。

② 最左匹配 — 方向对，但解释太浅

你说「B+ 树的问题」是对的，但面试官想听更具体的：

▎ 完整解释： 联合索引 (a,b,c) 在 B+ 树里的排序规则是先按 a 排，a 相同再按 b 排，b 相同再按 c 排。WHERE b=1 AND c=1 不给 a 的值，B+ 树的根节点和中间节点都是按 a 分叉的，不知道 a 就不知道往哪个子树走，只能全索引扫描，优化器干脆选全表扫描。

③ 索引失效 — 有一个知识点错误

│ IN 会导致索引失效   │ ❌ 错误！ │

IN 不会导致索引失效！ 这是面试里极高频的误解。

-- MySQL 会把它展开成多个等值查询，走 index range scan

只有当 IN 列表极长（几千个值），优化器认为全表扫描更快，才会放弃索引。

✅ 完整答案（4 种索引失效场景）

WHERE create_time >= '2025-01-01' ✅

-- ② 对索引列做运算
WHERE id + 1 = 10  ❌
WHERE id = 9       ✅

-- ③ 类型不匹配（隐式转换）

---
难点一：nextIndex 和 matchIndex 的并发更新问题

Leader 并发发送 AppendEntries 给 Follower，
可能先收到新 RPC 的回复，后收到旧 RPC 的回复。

❌ 错误做法：直接用回复里的 index 更新 nextIndex
→ 旧回复到达时，会把 nextIndex 往回拨，
  导致重复发送已确认的日志。

✅ 正确做法：只有当回复对应的 prevLogIndex
  大于当前 matchIndex 时才更新。
  判断回复是否过时：对比 reply 里的 term 和发送时的 term。

---
难点二：Figure 8 问题 — 不能提交上一任期的日志

这是论文里最反直觉的规则，Lab 里踩了会导致数据丢失：

场景：
  S1 是 Term2 的 Leader，把日志[Term2]复制到 S2，然后 crash
  S3 成为 Term3 的 Leader，又写了日志[Term3]
  S3 crash，S1 重新当选 Term4 Leader
  S1 看到 S2 有 [Term2] 的日志，并已经多数派了

❌ 错误：S1 直接 commit [Term2] 的日志
→ 如果 S3 以 Term3 重新当选，会覆盖掉这条日志，
  导致已 commit 的数据丢失！

✅ Raft 的规则：Leader 只能通过提交当前 Term 的日志，
  来「顺带」提交之前 Term 的日志。
  必须在 [Term2] 后面追加一条 [Term4] 的日志，
  一起复制到多数派，才能安全 commit。

---
难点三：快照（Snapshot）和日志复制的交互

问题：InstallSnapshot RPC 和 AppendEntries RPC 并发到达时，
     如果先处理了新 Snapshot，然后处理了旧 AppendEntries，
     会把日志状态回滚到快照之前。

✅ 解决：收到 AppendEntries 时，检查 prevLogIndex
  是否比当前 lastIncludedIndex 小，
  如果是，说明这是个过时的 RPC，直接丢弃。

① 隔离级别 — 有一个经典混淆

┌──────────┬─────────────────┬─────────────────────┐
│ 隔离级别 │   解决的问题    │       你说的        │
├──────────┼─────────────────┼─────────────────────┤
│ 读未提交 │ 无              │ ✅                  │
├──────────┼─────────────────┼─────────────────────┤
│ 读已提交 │ 脏读            │ ✅                  │
├──────────┼─────────────────┼─────────────────────┤
│ 可重复读 │ 不可重复读      │ ❌ 你说「解决幻读」 │
├──────────┼─────────────────┼─────────────────────┤
│ 串行化   │ 幻读 + 所有问题 │ ✅                  │
└──────────┴─────────────────┴─────────────────────┘

可重复读解决的是「不可重复读」，不是幻读。

脏读：      读到别人未提交的数据
不可重复读： 同一事务两次读同一行，值不同（别人改了）
幻读：      同一事务两次读，行数不同（别人插入/删除了）

MySQL InnoDB 的 RR 通过 MVCC + 间隙锁顺带防了大部分幻读，但这是实现细节，不是 RR 的定义。

---
② MVCC — 方向对，Read View 是关键缺口

你说「通过时间戳」——InnoDB 用的是事务 ID（trx_id，自增整数），不是时间戳。

Read View 是 MVCC 的核心，必须会：

每个事务开启时（RR级别），创建一个 Read View，记录：
┌─────────────────────────────────────────────┐
│ m_ids：当前活跃（未提交）的事务ID列表        │
│ min_trx_id：m_ids 中最小的 ID               │
│ max_trx_id：下一个将分配的事务 ID            │
│ creator_trx_id：当前事务自己的 ID            │
└─────────────────────────────────────────────┘

读一条记录时，检查记录的 trx_id：

trx_id < min_trx_id   → 已提交，可见 ✅
trx_id > max_trx_id   → 在我之后开启，不可见 ❌ → 顺 undo log 链往前找
trx_id 在 m_ids 里    → 开启时还未提交，不可见 ❌ → 往前找
trx_id = creator_id   → 自己写的，可见 ✅

undo log 就是每次修改前的旧版本，构成版本链，Read View 沿着链找第一个「可见」的版本。

---
③ 幻读场景 — 关键结论完全反了

这是这题最重要的考点，你的答案错了：

▎ ❌ 你说「UPDATE 影响 10 行」
▎ ✅ 实际 UPDATE 影响 11 行

原因：SELECT 和 UPDATE 使用完全不同的读机制。

┌─────────────────┬─────────────────────────────┐
│  快照读（Snapshot Read）    │  当前读（Current Read）      │
├─────────────────┼─────────────────────────────┤
│ 普通 SELECT     │ UPDATE / DELETE / INSERT     │
│                 │ SELECT ... FOR UPDATE        │
│                 │ SELECT ... LOCK IN SHARE MODE│
├─────────────────┼─────────────────────────────┤
│ 走 MVCC，读     │ 跳过 MVCC，直接读最新已      │
│ Read View 快照  │ 提交数据，加行锁/间隙锁      │
└─────────────────┴─────────────────────────────┘

完整过程：

BEGIN; -- 事务A，创建 Read View，活跃事务快照

SELECT COUNT(*) WHERE status=0; -- 快照读 → 10 条

-- 事务B INSERT 一条 status=0 并 COMMIT

SELECT COUNT(*) WHERE status=0; -- 快照读 → 仍然 10（Read View 没变）

UPDATE orders SET status=1 WHERE status=0;
-- ⚠️ 当前读！看到最新已提交数据 → 11 条
-- 更新影响 11 行！

SELECT COUNT(*) WHERE status=1;
-- 快照读，但自己更新的数据可见 → 返回 11！
-- 明明之前只看到10条，现在status=1却有11条 → 这就是幻读！

RR 级别下幻读没有完全消失，在 SELECT + UPDATE 混用时仍然可能出现。

---
✅ 完整推荐答案

▎ 会返回 11，尽管我从未'看到'过这条数据——这就是 RR 下幻读没有被完全消灭的经典场景。要彻底 ECT ... FOR UPDATE 加间隙锁。」

第 3 周：系统设计专项训练

系统设计是你目前最大的短板，需要建立框架。

万能四步框架：

Step 1：澄清需求（2分钟）
  「日活多少？数据量多大？延迟要求？一致性要求？」

Step 2：规模估算（2分钟）
  QPS = DAU × 每日操作次数 / 86400
  存储 = 每条记录大小 × 每日新增 × 保留天数

Step 3：整体架构（10分钟）
  数据从哪来 → 怎么处理 → 存哪里 → 怎么查

Step 4：深挖难点（10分钟）
  面试官会在最难的地方追问，准备好 3 个难点的详细方案

练习 3 道题，每道写在纸上：

① 设计微博热搜排行榜（Kafka + Redis ZSet + 滑动窗口）
② 设计一个分布式 ID 生成器（Snowflake / 号段模式）
③ 设计门票场景化投放系统（就是你做过的，用框架重新描述一遍）

推荐资料：
